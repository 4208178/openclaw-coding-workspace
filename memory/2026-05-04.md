## 🚨 今日关键事件

### 事件 1: Gateway 重启与代理会话恢复
- **时间**: 19:22
- **现象**: `coding` 代理会话超时，无法响应 `sessions_send`
- **根因**: Gateway 进程重启后，代理会话状态未正确恢复，处于"僵死"状态
- **解决方案**: 
  1. 执行 `openclaw gateway restart`
  2. 会话状态恢复为 `running`
  3. 但通信链路仍未打通（回复未路由回主会话）
- **经验教训**: 
  - Gateway 重启后，代理会话需要**主动触发**才能完全恢复
  - `sessions_send` 不可靠，应改用 `cron` + `isolated` 会话模式

### 事件 2: 通信链路故障
- **时间**: 19:25 - 19:35
- **现象**: 向 `coding` 发送消息后超时，无响应
- **根因**: 
  - 代理已生成回复（通过 `sessions_history` 确认）
  - 回复**未路由回主会话**（Channel 绑定或 `delivery` 配置问题）
- **解决方案**: 
  - 改用 `cron` 任务触发代理，使用 `isolated` 会话模式
  - 主动拉取 `sessions_history` 获取回复
- **经验教训**: 
  - `sessions_send` 适合**临时消息**，不适合**任务触发**
  - 需要检查 `bindings` 配置，确保回复能正确路由

### 事件 3: 会话启动失败
- **时间**: 22:05 - 22:10
- **现象**: 删除会话文件后重启 Gateway，`coding:main` 会话立即失败
- **根因**: 代理配置或模型配置可能有问题，导致会话无法稳定运行
- **解决方案**: 
  - 改用 `cron` + `isolated` 模式作为长期解决方案
  - 不再依赖 `coding:main` 主会话

## 🛠️ 技术决策与复盘

### 决策 1: 使用 `cron` + `isolated` 会话模式
- **背景**: `sessions_send` 无法可靠激活代理
- **方案**: 使用 `cron` 任务创建 `isolated` 会话，强制执行任务
- **结果**: 成功触发代理执行，但回复仍需手动拉取
- **经验**: 
  - `sessions_send` 适合**临时消息**，不适合**任务触发**
  - `cron` + `isolated` 适合**批量任务**和**后台作业**

### 决策 2: 持久化团队唤醒机制
- **背景**: 系统重启后代理会话可能丢失
- **方案**: 
  - 写入 `HEARTBEAT.md` 定义唤醒逻辑
  - 创建 `Auto-Wake-Team` cron 任务
- **状态**: 已配置，待验证系统重启后是否生效
