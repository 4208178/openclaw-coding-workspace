# ADR 0002: 技术栈选择 (Node.js + TypeScript + Fastify)

**状态**: 已批准 (Approved)  
**日期**: 2026-05-06  
**决策者**: CTO (蜜蜂)  
**批准者**: CEO (田螺)

## 上下文 (Context)

根据 CEO 授权，CTO 需自主选择技术栈以完成“项目初始化与架构设计验证”任务。项目目标为验证 CTO 与子代理协作流程，需满足：
1. **快速迭代**：支持快速原型开发与验证。
2. **类型安全**：减少运行时错误，提升代码质量。
3. **生态成熟**：丰富的第三方库与社区支持。
4. **可维护性**：易于团队协作与长期维护。

## 决策 (Decision)

我们选择以下技术栈：

| 类别 | 技术选型 | 理由 |
| :--- | :--- | :--- |
| **语言** | TypeScript | 静态类型检查，提升代码质量与可维护性 |
| **运行时** | Node.js (v20+) | 事件驱动，适合 I/O 密集型服务，生态丰富 |
| **框架** | Fastify | 高性能，插件生态，优于 Express 的现代框架 |
| **测试** | Jest + Supertest | 成熟测试框架，支持覆盖率统计 |
| **代码规范** | ESLint + Prettier | 统一代码风格，自动化格式化 |
| **CI/CD** | GitHub Actions | 与 GitHub 无缝集成，无需额外配置 |

## 理由 (Rationale)

### 1. TypeScript vs JavaScript
- **优势**：静态类型检查可捕获 15-20% 的潜在错误（微软研究数据）。
- **成本**：学习曲线略高，但团队已有基础。
- **结论**：符合 CTO“代码质量 > 速度”原则。

### 2. Fastify vs Express
- **性能**：Fastify 比 Express 快 2-3 倍（官方基准测试）。
- **插件生态**：`@fastify/autoload` 支持模块化路由，优于 Express 的手动配置。
- **类型支持**：Fastify 原生支持 TypeScript，Express 需额外配置。
- **结论**：Fastify 更适合长期维护的项目。

### 3. Jest vs Mocha
- **开箱即用**：Jest 内置断言、mock、覆盖率统计，无需额外配置。
- **性能**：并行测试执行，速度更快。
- **社区**：React/Next.js 社区首选，文档丰富。
- **结论**：降低测试门槛，提升测试覆盖率。

## 后果 (Consequences)

**正面**：
- 代码质量显著提升（类型安全 + 自动化测试）。
- 开发效率提高（热重载 + 快速测试）。
- CI/CD 自动化（GitHub Actions 自动运行测试与构建）。

**负面**：
- 初始配置时间较长（约 1-2 小时）。
- TypeScript 编译增加构建时间（约 5-10 秒）。

**风险**：
- 无重大风险，技术栈成熟且社区活跃。
